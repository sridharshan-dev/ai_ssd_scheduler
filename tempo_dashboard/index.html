static inline void nvme_setup_tempo_rw(struct nvme_command *cmd, 
                                      u16 slack_us, u8 sla_tier) {
    cmd->rw.rsvd2 = 0;

    cmd->rw.cdw13 = cpu_to_le32(((u32)slack_us << 16) | (u32)sla_tier);
}

Q1: Why can't the host operating system or PyTorch do this scheduling?
The host has no physical visibility into the SSD's internal flash channels, LUNs, or FTL state. A 185 µs write program or 1.0 ms block erase happens entirely within the flash memory controller. Any host-only scheduler dispatching commands into the NVMe queue will randomly collide with busy dies. Only the controller firmware has the hardware state to make collision-free arbitration decisions.
Q2: Does TEMPO add latency or computational overhead to the SSD controller?
No. TEMPO's arbitration algorithm is provably bounded at $O(Q \times P) \le 128$ operations for a queue depth of 32. In our native C firmware prototype benchmarked on an ARM Cortex-R8 @ 800 MHz, it takes only 1,393 cycles (1.74 µs). This is less than 5% of flash sense time (36.0 µs) and executes concurrently during DMA transfers, resulting in zero added latency.
Q3: How does TEMPO maintain standard NVMe compatibility?
TEMPO utilizes Command Dword 13 in the 64-byte NVMe Submission Queue Entry (SQE). Under the official NVMe 2.0 specification, Dword 13 is designated for vendor-specific command parameters. Standard off-the-shelf NVMe drives simply ignore Dword 13, making TEMPO 100% backward-compatible with legacy hardware.
Q4: Does reordering requests affect SSD write endurance or wear leveling?
No. TEMPO only reorders in-flight queue entries; it does not change Flash Translation Layer (FTL) wear-leveling algorithms or increase write amplification. In fact, by eliminating 25.4% of wasted speculative read attempts that miss their deadline, TEMPO reduces total controller and NAND flash stress.
